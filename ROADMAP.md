# DocuMind — дорожная карта проекта

RAG-сервис «задай вопрос своей документации»: загрузка документов, асинхронная
индексация через Kafka, гибридный поиск (pgvector + полнотекстовый) и ответы LLM
с цитатами-источниками.

Порядок этапов не случаен: каждый следующий опирается на предыдущий, а проект
в любой момент остаётся в деплоепригодном состоянии.

Каркас репозитория и окружение разработки.

- [x] uv-проект, ruff + mypy + pre-commit
- [x] Docker Compose: PostgreSQL 17 + pgvector, Redis
- [x] CI на GitHub Actions (lint → типы → тесты)

**Готово, когда:** `docker compose up` поднимает стек, CI зелёный с первого коммита.

## M2. Индексация документов 🔄

Конвейер «документ → чанки с векторами» (пока синхронно, через фоновые задачи).

- [x] Парсер PDF/Markdown (HTML/URL — отложено)
- [x] Чанкер с сохранением пути по заголовкам (`heading_path`)
- [x] Эмбеддинги OpenAI (обёртка за интерфейсом, для тестов — фейк)
- [x] Расширение `vector` в миграции, колонка `embedding`, индекс HNSW
- [x] Фоновая индексация через BackgroundTasks (временное решение, заменено Kafka в M3)
- [ ] Загрузка и индексация документов по URL

**Готово, когда:** загруженный документ доходит до статуса `ready`, в базе чанки с векторами.
*(Для файлов — принято: 7 чанков фикстуры проиндексированы, векторы в базе,
битый PDF честно уходит в `failed` с текстом ошибки.)*

## M3. Kafka-пайплайн ✅

Вынос индексации в отдельного воркера.

- [x] Продюсер события `documents.ingestion.requested`
- [x] Воркер-консюмер: manual commit, ретраи, идемпотентность
- [x] DLQ для «ядовитых» сообщений

**Готово, когда:** убийство воркера посреди обработки не ломает и не дублирует документ.
*(Принято в Docker: `kill -9` воркера во время обработки → после перезапуска документ
`ready`, ровно 7 чанков, не 14. Невалидные сообщения уходят в DLQ, закладка
фиксируется, воркер продолжает работу и обрабатывает следующие документы.)*

## M4. RAG-чат ✅

То, ради чего всё затевалось.

- [x] Гибридный поиск: pgvector + полнотекстовый, слияние RRF
- [x] Промпт с нумерованными источниками
- [x] Стриминг ответа через SSE
- [x] Сохранение сообщений и цитат (message ↔ chunk)
- [x] История диалогов: создание, список, чтение с цитатами, удаление
- [x] Поиск по документации в интернете (флаг `web_search`): наборы официальных сайтов
  по направлениям (`web_profile`, файл `backend/app/rag/web_profiles.json`), поисковый API
  Tavily с фильтром по доменам, перефразирование вопроса в английский запрос, PDF,
  события `status` в потоке, кэш в Redis (перефразированные запросы, найденные страницы)
- [x] Личные списки сайтов: пользователь сам заводит наборы доменов (`/my-web-profiles`,
  до 10 списков по 50 сайтов) и выбирает их в вопросе полем `my_web_profile_id`. Страницы
  по ним сами не скачиваются (защита от SSRF): берётся только то, что прислал Tavily,
  поэтому без `TAVILY_API_KEY` такие списки ничего не находят

**Готово, когда:** вопрос в Swagger → поток ответа со сносками на конкретные куски документа.
*(Принято с настоящим OpenAI клиентом SSE (`httpx`), а не в Swagger UI: ответ со ссылками
`[n]` на куски документа; вопрос без ответа даёт фиксированный отказ без вызова модели;
чужой диалог и чужой документ — 404; обрыв потока не оставляет неполного сообщения;
после переиндексации и удаления документа история читается, копии цитат на месте.
Поиск по интернету принят на вопросах про FastAPI и `asyncio` без единого документа
у пользователя. Порог релевантности векторного поиска не задан: решение отложено.
Веб-поиск проверен на профилях `backend` и `analyst` (вопросы про FastAPI, Kafka и
спецификацию BPMN из PDF): сайты вне профиля отбрасываются в коде, а не только поисковиком.
Личные списки проверены на двух пользователях: чужой список недоступен ни для чтения, ни
для изменения, ни в вопросе; страниц сервер сам не скачивает.)*

## M5. Redis-слой

- [ ] Кэш ответов (ключ — нормализованный вопрос + id документов, `X-Cache` заголовок)
- [x] Rate limiting на пользователя: фиксированные окна в Redis (минута, у веб-вопросов ещё
  сутки), сверх лимита 429 с `Retry-After`; пределы в `RATE_LIMIT_*`, ограничены вопросы
  (свои документы и интернет считаются отдельно) и загрузка документов
- [x] Защита входа: попытки считаются по связке «адрес + аккаунт» (10 за 15 минут) и по адресу
  (30), регистрации по адресу (10 в час); верный пароль после исчерпания лимита тоже получает 429
- [x] Потолки загрузки: файл не больше 20 МБ (`MAX_UPLOAD_BYTES`, лишнее тело отсекает
  `BodySizeLimitMiddleware` до разбора формы), не больше 50 документов на пользователя
  (`MAX_DOCUMENTS_PER_USER`)

*Заготовка уже есть: `backend/app/core/cache.py` (интерфейс `Cache`, `RedisCache`,
`InMemoryCache`; клиент создаётся и закрывается в `lifespan`). Её использует кэш страниц
веб-поиска (ключи `web:rewrite:v2:…`, `web:search:v2:…`, `web:page:v1:…`, срок
`WEB_CACHE_TTL_SECONDS`). Кэш общий для всех: это публичные страницы, личных данных в нём нет.
Для ограничения частоты в `Cache` добавлен атомарный счётчик окна `incr`, зависимость
`RateLimit` лежит в `backend/app/api/rate_limit.py`. Кэш ответов не сделан.*

**Готово, когда:** повторный вопрос отдаётся мгновенно из кэша, превышение лимита — 429.
